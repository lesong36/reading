# 问答延迟拆解与连接复用（0.2.71）

2026-10-06，在 0.2.70 的关闭／最少思考模式上继续测量。保持 LangChain 1.4.3、现有模型和依赖，不修改服务地址、Key、历史或回答规则。

## 落地改动

`question-engine/question_engine.py`：HTTP 连接闲置保留从默认 5 秒延长到 120 秒，保留原先 100 个总连接、20 个空闲连接的上限和最多 4 个模型客户端缓存。输入追问超过 5 秒时，有机会继续使用同一连接。模型、Key、思考强度或系统代理变化仍隔离客户端。没有新增保活网络请求、自动重试或模型调用。服务端若主动关闭连接，客户端仍需重新连接。

对应配置含义见 [HTTPX 连接限制](https://www.python-httpx.org/advanced/resource-limits/)，本项目使用的 `httpx2` 已通过本地构造函数与实际 socket 测试确认相同的默认值和接口。

## 诊断依据

临时测试包装器只记录单调时钟、模型名、HTTP 状态、Content-Type、TCP/TLS 建立次数和文字片段数；不写入请求、API Key、服务响应头或原始网络内容。真实调用只使用公开语法题及已配置服务。计时从引擎收到本轮请求开始。

- 三个模型都返回 SSE 流，存在多次文字增量，客户端没有等待完整 JSON 再显示。
- 模型客户端首次准备约 118–135 ms，其后从收到请求到送入网络通常约 1–6 ms。Python 首段发出到 Swift 回调在本次测试中约 1 ms。
- GPT、Claude 首字等待的较大部分发生在请求已经送入网络之后。这个区间包含网络、网关排队与模型计算，无法仅凭客户端时间进一步精确拆开。
- 7 秒输入间隔对照中，原默认 GPT／Claude 追问重新建立 TCP 与 TLS；120 秒策略成功复用，两项建立事件由 2 降到 0。DeepSeek 的该链路仍重新连接，说明延长本地保留时间没有保证所有服务都保持连接。
- 已复用连接的一次 GPT 调用从网络发出到响应头仍等待约 8.19 秒，首字约 8.20 秒；应用侧数毫秒优化无法消除这种上游延迟。

系统提示从 1525 UTF-8 字节缩到 795 字节。相同问题、无图片与历史、思考优先速度，每组两次，第二轮反转条件与模型顺序。

本轮没有改善，也没有完成更广的回答质量验证。因此保留现有原文纠错、代词格判断和追问规则，没有为了减少字数修改正式提示。官方[延迟优化指南](https://developers.openai.com/api/docs/guides/latency-optimization)也提示缩减输入的收益与具体负载有关，不能从字数直接推断首字降幅。

## 连接策略实测

每个模型、每种策略各两次，第二次在上次完成后等待 7 秒。24 次真实请求（提示对照 12 次、连接对照 12 次）全部成功，并均建议标准英语应将 I 改为 me。这里只验证了这道题的回答，没有宣称整体准确率。

连接复用对照第二次请求首字：GPT 1.91 s → 8.20 s，Claude 1.71 s → 1.89 s，DeepSeek 1.13 s → 1.35 s。虽然 GPT／Claude 避免了重连，本组数据没有证明首字整体更快，尤其 GPT 有明显上游波动。样本小且策略按顺序测试，不能用作服务 SLA 或因果速度结论。采用该改动的依据是确实避免了输入间隔后的不必要重连，而不是这些耗时比较。[原始记录与统计](QUESTION_CONNECTION_PERFORMANCE.json)。

## 回归与范围

- 新回归在原 5 秒设置下失败：等待 6 秒后服务端看到新连接端口。120 秒设置下通过，使用同一 socket，且仍只有两次原始问题请求。
- Python 39 项通过，包含连接复用、代理变化隔离、取消、流完整性和三协议 SDK；Swift 190 项通过（warnings-as-errors）。语法编译与 diff 空白检查通过。
- 改动仅涉及 `question_engine.py`、`tests/test_engine.py`、`VERSION` 与本 README／验证记录；复用现有客户端池，没有增加缓存答案层或依赖。
- 首次请求、服务器主动关闭连接、服务端排队与思考耗时仍受服务制约。没有切换用户模型、把 Key 发到新服务或牺牲原文完整性。
