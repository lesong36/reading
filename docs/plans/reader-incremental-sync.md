# ReadingMaster 增量同步实施计划（2026-11-16）

## 目标与范围
按用户交接八项要求替换普通学习状态及词库全量协议。保留现有未提交修改，不复用 VocabMaster 私有表，不清除旧数据，不自动回退全量同步。

## 分阶段实施
1. 基线：确认 index.html:4332 初始化读取、5874 合并读取、5906 全量 upsert，supabase/vocabulary-sync-v2.sql 全量重建；保存既有测试结果。
2. 服务端：独立实体、不可变答题事件、操作确认、用户事务计数器；同一用户锁覆盖计数分配与提交，避免晚提交遗漏。独立 SQL 文件，RLS/权限最小化，50条/128KiB上传与50条/100KiB下载限制。
3. 客户端：独立 IndexedDB 实体/outbox/cursor，账号隔离，先持久化后发送，只删除明确确认ID；50条/100KiB实际UTF8请求预算，原子落页后推进游标。
4. 接入：替换学习状态和生词旧协议调用，保留本机功能；逐题/逐文章/逐收藏记录，显示真实待确认数量、成功时间、协议和应用版本。
5. 迁移：冻结已迁移账号旧协议，旧数据只读保留，有界迁移及ID/数量/内容校验。不得以初次导入为日常同步路径。
6. 验证：真实本机PostgreSQL验证SQL、权限、幂等、事务顺序和1万/10万历史查询计划；客户端断网/响应丢失/刷新/乱序/删除恢复/切账号/过期游标；现有Node回归及Chrome/Edge独立浏览器验证。
7. 发布准备：部署顺序、灰度门槛、回滚方案和证据清单。只有真实完成的检查才能标为通过；生产账号抓包及小流量若缺少连接条件则明确保留待验收项，不能声称完成上线。

## 验收标准
普通新增一道答案仅发送本次实体操作和事件，不发送历史；空闲不读取旧快照；分页条数与字节均有边界；重复操作返回原确认；冲突不吞数据；游标永不越过未提交事务；失败保留队列且可见；不同账号无法读取彼此数据。
迁移前后ID/数量/哈希一致，旧客户端不能覆盖已迁移账号。10k/100k查询使用(user_id, cursor)索引，保存EXPLAIN ANALYZE、请求/响应大小。mock结果单列，不能代替实际数据库和生产证据。

## 风险与处置
旧本机数据缺少账号标签：明确归属后迁入，不自动把上一账号快照导入新账号。并发同实体：基准版本冲突保留待处理操作。迁移中断：保留旧数据与进度，可重入。旧版本回滚：不撤销保护触发器，禁止重启旧写入协议。
